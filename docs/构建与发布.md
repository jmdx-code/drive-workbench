# 构建与发布

源码与便携版公开于 https://github.com/jmdx-code/drive-workbench 。不上传个人 OAuth 配置、token、账号数据库、参考项目、测试截图或旧构建。

## 开发

Node.js 24，`npm ci`、`npm test`、`npm run build`。`npm run package` 按当前操作系统打包：Windows x64 使用现有便携打包器；macOS 使用 Electron Packager，原生构建当前架构。不能在 Windows 上本地验证 Mac 包，请使用 Actions 的两个 Mac runner。

## 发布新版本

1. 使用 `npm version 1.4.0 --no-git-tag-version` 同步更新 package.json 和 package-lock.json（版本号举例）。
2. 更新发布说明，运行测试，提交并推送 main。
3. GitHub Releases → Draft a new release，创建标签 `v1.4.0`，目标选择刚才提交的 main，点击 Publish release。
4. Release portable apps 工作流自动并行构建三个平台，版本标签必须与 package.json 完全相同。不要重复使用旧标签指向不同源码。
5. 全部测试与构建通过后，工作流自动为三个 ZIP 生成 Ed25519 签名清单，再上传 Windows-x64、macOS-arm64、macOS-x64 ZIP、SHA256SUMS.txt、UPDATE-MANIFEST.json 与 UPDATE-MANIFEST.sig。签名缺失、私钥不匹配或构建失败时不会发布。日常不需要下载文件或手工签名；同一提交的临时失败可在 Actions 重跑。
6. 软件从公开 Release 自动检查更新，不使用内置 GitHub 令牌；发布文件可以匿名下载。GitHub 接口暂不可达、限流或资产仍在构建时保留当前版本，设置中显示错误，可稍后重试。

工作流手动触发可输入 `main` 并保持 publish=false，先进行三平台构建测试，不上传发布资产；此时构建固定到触发时的提交。恢复已有发布标签时，输入该标签并显式勾选 publish，仍会严格核验版本一致。只有 publish 任务有仓库写权限，构建任务为只读；第三方 Actions 固定到提交 SHA。

## 便携更新

更新器只接收 GitHub HTTPS 下载地址及匹配平台、架构的稳定版本。使用客户端固定公钥验证清单原始字节的 Ed25519 签名，核对版本、平台、架构、大小与 SHA256 后才下载/复用缓存，安装前再次校验包。缺失或无效签名不回退至旧哈希方案。确认更新且无在途任务后退出，由独立辅助进程等待退出、解压并替换程序目录，再启动应用。用户数据目录独立，不参与替换；旧程序保留，替换失败时回滚。更新不会自动继续此前暂停的云端任务。

## 签名的一次性配置

客户端公钥位于 `core/update-key.ts`；此次新私钥已保存在仓库外 `C:\Users\jj\.drive-workbench-signing\update-ed25519-private.pem`，Windows ACL 仅授予当前用户访问。不要提交私钥、不要贴到聊天或日志。可将它保存到加密离线备份；遗失后不能用新密钥无缝更新已有客户端。

在 GitHub 仓库 Settings → Environments 创建 `release-signing`，配置仅允许受保护发布来源，并设置 required reviewers，避免有源码/Release 写权限的人直接读取签名密钥。新增 Environment Secret `UPDATE_SIGNING_PRIVATE_KEY`，值为上述 PEM 文件完整内容。只需配置一次；以后正常发布触发 CI 自动签名，如启用审批则在 Actions 中批准发布环境即可。不要将 Secret 放在普通源码文件或未保护的日志中。

2026-10-22 已按开发者授权完成 `jmdx-code/drive-workbench` 的远端配置：`release-signing` Environment 已创建，允许 main 分支和 v* 标签，要求 jmdx-code 审批（允许本人批准自己触发的发布），`UPDATE_SIGNING_PRIVATE_KEY` 已经 gh CLI 本地加密上传；上传前已核对与客户端固定公钥一致。环境规则和 Secret 元数据已回读验证。日常不需重新配置或手工签名，只在构建完成后批准发布。本地修改尚未推送，未创建或触发 Release。

其他仓库迁移时，可在核对目标仓库与环境保护后使用 `Get-Content -Raw -LiteralPath 'C:\Users\jj\.drive-workbench-signing\update-ed25519-private.pem' | gh secret set UPDATE_SIGNING_PRIVATE_KEY --repo jmdx-code/drive-workbench --env release-signing`。命令将私钥直接经管道传给 gh，由其加密上传，不回显内容。不要无故重复生成/轮换密钥；build-only 不需要私钥。

`node scripts/sign-release-test.mjs` 使用临时测试密钥验证流水线，不需要生产私钥。本地恢复签名可用 `WB_UPDATE_SIGNING_KEY_FILE` 指定仓库外文件，再运行 `node scripts/sign-release.mjs <三个平台ZIP所在目录>`；这是可选恢复路径，日常由 CI 执行。

旧客户端首次迁移：保留 SHA256SUMS.txt 供旧版完成一次升级；旧版不能追溯验证签名。高保证部署应从可信渠道核对后手工安装首个带固定公钥的版本。新客户端只接受签名清单，不允许降级至未签名更新。GitHub 内容写权限与签名 Environment 的审批/密钥权限必须分离；若同一攻击者能修改并批准签名 job，仍可能签署恶意包。

Mac 包执行 ad-hoc 签名与 codesign 校验，未做 Developer ID 签名及公证。Gatekeeper 首次打开的提示和钥匙串访问仍需在真实用户 Mac 上验证，runner 启动测试不能替代全部用户环境。若要完全标准的外部分发体验，需要 Apple Developer 证书与公证凭据；不得把这些凭据写入仓库。
