# 安全审核报告（2026-10-22）

## 1. 项目概况与结论

审核对象：Drive Workbench 1.3.5，当前工作区及本地可达 Git 历史。语言为 TypeScript/JavaScript，界面为 React 19，桌面框架为 Electron，使用 Vite 构建、Vitest 测试、Node 内置 SQLite 保存数据。包管理器为 npm；依赖清单为 `package.json`，唯一锁文件为 `package-lock.json`。没有发现其他语言的依赖清单、浏览器扩展 manifest、Web 后端或移动端工程。

共有 **18 个直接依赖（4 个生产依赖、14 个开发依赖）**，锁文件最初包含 179 个安装条目，移除 rcedit 并引入 resedit 后为 **176 个依赖安装条目**，其中包含不同平台的可选二进制包。Electron 虽列在 devDependencies，仍是发布程序的运行时，不能当作仅开发环境风险排除。

本次修复 OAuth 回调异常、发布版开发模式开关、CSV 输出防护缺口，并收紧 IPC/CSP/浏览器权限；Electron 从 44.9.1 补丁升级到 44.9.3。经开发者选择，已加入 Ed25519 更新签名验证并改为 CI 自动签名发布，rcedit 已替换为 resedit。未发现已确认适用于当前锁定版本的 Critical/High 依赖公告，未发现真实凭据泄露。远端发布 Secret/Environment 已按开发者后续授权配置并回读验证；本地源码和工作流尚未推送，实际签名发布尚未运行。

**“未发现”不是不存在漏洞的保证。** 本次是源代码审查、公开漏洞检索、本地扫描与隔离测试；未登录真实 Google 账号执行攻击测试，未访问用户的应用数据目录，未审计 npm 包的全部源代码或 Electron 原生二进制内部实现。macOS 动态行为、远端 GitHub 仓库权限配置及不可达/已被清理的历史对象均待确认。

## 3. 已修复问题、利用条件与改动

### SEC-01：OAuth 回调服务拒绝服务

原监听器直接执行 `new URL(req.url, redirect)`，没有异常处理。授权期间能连接临时 loopback 端口的本地程序可发送 `http://[` 之类畸形 HTTP request-target，使解析抛出异常，存在终止主进程的风险。不要求知道 OAuth state；远程互联网不能直接连接该监听地址，因此评为 Medium。

已捕获解析错误并返回 HTTP 400；限定 GET、准确 Host、callback origin 与路径，继续保留随机 state、恒时比较和 PKCE。回调响应增加 `Cache-Control: no-store`、`Referrer-Policy: no-referrer`。同时提前观察授权结果 Promise 的拒绝，避免系统浏览器尚在打开时收到取消或超时导致未处理拒绝。错误仍通过原有 await 正常向上返回，没有吞掉业务失败。

回归：通过原生 HTTP 请求发送畸形 URL、POST、错误 Host、不同 origin 的绝对 URL，均返回 400；随后合法 callback 仍成功完成授权。真实桌面授权取消流程也通过隔离 UI 测试。

### SEC-02：发布程序可进入开发模式

原 `--dev` 检测没有排除 `app.isPackaged`。攻击者需要诱导用户使用带此参数的启动命令/快捷方式，并控制本地 5173 端口服务，才能让应用加载其页面。该页面可使用授权管理、文件操作等业务 IPC；本次未证明突破 Electron 沙箱到任意原生代码执行，因此不夸大为无条件远程 RCE。

已将开发模式限定为 `!app.isPackaged && process.argv.includes('--dev')`。正常源码开发仍可用；发布程序始终使用本地打包页面与对应 IPC 来源检查。已实际打包 Windows 程序并以 `--dev` 启动，确认仍加载 file: 生产页面，IPC、CSP 和沙箱验证通过。

### SEC-03：CSV 公式注入防护缺口

攻击者可控制共享文件名等网盘数据；用户导出报告并用会解释 CSV 公式的电子表格软件打开时可能触发。原任务报告遗漏 LF，两个导出入口也未处理空白后紧跟公式字符的情况。具体执行行为取决于表格软件/导入选项，未在本机 Excel 执行恶意公式，不能据此宣称已经复现命令执行。

新增共享 `csvCell()`：对以 TAB/CR/LF 开头，或以空白后紧跟 `= + - @` 开头的字段添加单引号；保留 CSV 双引号转义。目录 CSV 与任务报告共用此实现，避免两个入口规则漂移。新增公式前缀、控制字符、普通文本、逗号/双引号及真实目录导出入口的回归用例。导出中的可疑文本会多一个用于防公式执行的单引号，这是安全修复预期行为。

### SEC-04：渲染进程边界加固

IPC 现在还要求 `event.senderFrame === window.webContents.mainFrame`，避免将来同 URL 的子 frame 获得特权业务入口。生产 CSP 移除对开发 WebSocket 地址的访问许可，增加 `frame-src 'none'`、`form-action 'none'`；开发服务器单独注入 HMR 所需 WebSocket 许可。默认拒绝浏览器权限请求和权限检查，并显式阻止 webview 挂载；应用没有使用设备/位置/通知等浏览器权限的业务功能。

利用此前较宽策略仍需要先得到渲染代码执行或 frame 注入能力，本次没有发现这样的入口，因此记录为 Low 加固。新增安全 UI 检查验证正确主 frame 可调用 IPC，缺失/伪造 frame、错误 sender 被拒绝，定位权限返回 denied，沙箱和生产 CSP 生效。原有复制链接、扫描、导出等业务回归通过。

### SEC-05：Electron 补丁更新

已同步更新 manifest 和锁文件至 44.9.3，未升级到 45。官方 44.9.3 说明回补了 ANGLE、Chromium、PDFium、Skia、V8 的上游修复；本次没有找到足以精确绑定某个 CVE 到项目输入路径的公开证据，所以按预防性补丁更新记录，不杜撰 CVE 或宣称已修复确定可利用的 High 漏洞。渲染器显示本地界面，主进程使用网络接口，原生图片处理也在使用，不能仅凭“Electron 是开发依赖”忽略运行时补丁。依据：[官方 44.9.3 发布说明](https://github.com/electron/electron/releases/tag/v44.9.3)。

## 7. 经开发者选择完成的方案与剩余配置

### SEC-06：Ed25519 更新身份验证与 CI 自动签名

利用前提是攻击者获得固定 GitHub 仓库的 release/CI 发布写权限，或能替换该权限域提供的包与哈希。当前 SHA256 能发现损坏/单独缓存篡改，但当包和 SHA256SUMS 同时被替换时不能识别攻击；Windows 没有验证预期 Authenticode 发布者；macOS 使用 `identity: '-'` 的 ad-hoc 签名，`codesign --verify` 仅验证内容完整性，不能证明是本项目认可的发布者。替换包随后会执行，因此条件成立时影响 High；并没有发现仓库已被入侵。

开发者选定 Ed25519，随后明确要求日常无需下载和手工签名，现已实现 **GitHub Actions 自动签名并发布**。客户端固定新公钥，先验证 UPDATE-MANIFEST.json 原始字节对应的 64 字节 Ed25519 签名，再读取其中绑定的版本、平台、架构、包名、字节数与 SHA256。缺签、错误签名、其他密钥、重复资产、不匹配平台或大小一律拒绝，不回退到旧 SHA256SUMS。安装前再次检查下载包。

`scripts/sign-release.mjs` 在三个构建完成后为准确的三个 ZIP 签署清单，检查输入私钥必须匹配客户端公钥。签名 job 使用纯 Node 内置模块和仓库内验签代码，不执行 npm 安装或业务构建脚本。签名私钥仅注入签名步骤；GH_TOKEN 仅注入上传步骤。发布仍保留旧 SHA256SUMS.txt 兼容一次旧客户端迁移。

已生成的新私钥保存在 `C:\Users\jj\.drive-workbench-signing\update-ed25519-private.pem`，目录 ACL 已验证仅当前用户 FullControl。代码仓库和便携包中只有公钥；没有打印或提交私钥。开发者随后授权代为配置，已使用 gh CLI 经标准输入本地加密上传到 `jmdx-code/drive-workbench` 的 `release-signing` Environment Secret `UPDATE_SIGNING_PRIVATE_KEY`；上传前核对私钥与固定公钥一致。配置仅允许 main 分支与 v* 标签，要求 jmdx-code 审批，允许其批准自己触发的发布以适配个人仓库。已通过 API 回读环境规则和 Secret 名称/更新时间验证，记录见 `security/github-signing-environment.json`，未读取服务端 Secret 明文。日常无需下载或手工签名，构建完成后批准发布即可。本地工作流尚未推送，未触发远端发布。

## 8. 剩余风险与后续建议

SEC-09：safeStorage 保护连接凭据；账号邮箱、文件名、权限、任务历史和 resource key 等元数据仍保存在普通 SQLite 或导出文件中。本地同用户读取权限、备份/磁盘丢失可能造成隐私泄露。SQLite 删除记录加 WAL checkpoint 不保证旧页、操作系统快照和备份的物理擦除；这不是“发现 refresh token 明文保存”。建议按数据敏感度选择全盘加密/用户目录 ACL、备份策略、记录保留周期；若要求加密全部任务数据库或安全擦除，需另定迁移和恢复方案。

建议 CI 增加依赖审计/密钥扫描门禁，在签名发布方案确定后保护发布环境、双人审批及签名权限。确认远端分支保护、Actions 环境保护和仓库 MFA 状态；这些设置不在本地 YAML 中，当前待确认。Linux 未列为便携发行目标，若将来支持，需要额外拒绝 safeStorage 的弱 `basic_text` 后端并做系统凭据存储验证。
